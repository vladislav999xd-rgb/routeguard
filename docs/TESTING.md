## Обязательный release-прогон

Команды выполняются из корня проекта, если не указано иное:

```bash
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test core.tests -v 2
cd frontend
npm run typecheck
npm audit --omit=dev
npm run build
npx playwright test
```

Проваленные и недоступные проверки нельзя записывать как успешные. Актуальный локальный результат приведён ниже и не заменяет PostgreSQL-проверку.

Базовые workflow-тесты покрывают синтетические сценарии P001–P020, изоляцию демосессий, отсутствие мутаций при GET, стабильность `completed_at`, обязательное подтверждение, запрет прошедшего слота, ограничения активной записи и идемпотентность бронирования.

P0-регрессии дополнительно проверяют:

- правдивую многоэлементную историю P019: создание маршрута, шаги, документы, завершения и итоговый статус представлены отдельными `AuditEvent` в детерминированном обратном хронологическом порядке;

- `Idempotency-Key` контакта: повторный запрос возвращает тот же `ContactResult` без второго события аудита;
- сериализацию структурированных контактов и контекст помощника: число попыток, последний результат и ближайшая задача;
- отклонение `POST /routes/` без согласованного плана шагов с кодом `route_plan_required`;
- отклонение мутации чужого workspace без изменений записи, слота, шага, событий и задач;
- snapshot-формулы `dashboard.analytics` и изоляцию их результатов по workspace;
- декодирование percent-encoded имени БД, пользователя и пароля из `DATABASE_URL`.

## Формулы snapshot-аналитики

Все запросы ограничены текущим workspace. Дата среза `as_of` — `Workspace.demo_date` для демо и локальная календарная дата для постоянного workspace.

| Поле | Формула |
|---|---|
| `eligible_routes` | все маршруты, кроме `cancelled` |
| `completed_routes` | маршруты со статусом `completed` |
| `incomplete_routes` | маршруты со статусом `draft` или `active` |
| `completion_rate_percent` | `completed_routes / eligible_routes × 100`, округление до 0,1; при нуле — `0` |
| `overdue_routes` | `draft/active`, где `due_date < as_of` или `attention_reason = overdue`; один маршрут считается один раз |
| `missed_appointments` | записи со статусом `missed` |
| `cancelled_appointments` | записи со статусом `cancelled` |
| `open_tasks` | задачи со статусом `open` |
| `due_tasks` | открытые задачи с `due_at.date <= as_of` |
| `completed_tasks` | задачи со статусом `done` |

Это текущий снимок всех сохранённых данных workspace, а не временной отчёт за период.

## Browser coverage

Playwright-спеки предназначены для проверки:

- пути «лендинг → демо → обзор → очередь → карточка → помощник звонка»;
- lazy-загрузки аналитики;
- responsive-представления на мобильном, планшетном и desktop viewport;
- семи сцен лендинга, WebGL/HTML fallback, управления движением и отсутствия горизонтальной прокрутки;
- P013 mutation journey: звонок с callback, видимая история контакта, повторная запись, завершение обязательного этапа и маршрута.

Скриншоты являются вспомогательными артефактами и не заменяют функциональные утверждения.

## PostgreSQL перед выпуском

SQLite используется только как быстрая локальная база. Перед production-выпуском тот же backend-набор выполняется на PostgreSQL 14:

```bash
set DATABASE_URL=postgresql://user:password@localhost:5432/routeguard_test
python manage.py test core.tests -v 2
```

Блокировки `select_for_update`, частичные уникальные ограничения и конкурентное занятие слота нельзя считать production-проверенными по одному SQLite-прогону. PostgreSQL-тест должен моделировать независимые транзакции; успешной остаётся только одна операция.

## Ручной smoke-check

1. Открыть новое гостевое демо и проверить наличие P001–P020.
2. В P019 увидеть несколько типизированных событий, а не одну сводную строку.
3. В P001 убедиться, что до подтверждения нельзя записать или завершить шаг; затем подтвердить маршрут.
4. В P013 пройти неявку → follow-up-задачу → повторную запись → завершение второго шага и маршрута.
5. В P016 сохранить будущий callback, повторить сохранение и проверить одну актуальную задачу и видимую историю контактов.
6. В P015 проверить отклонение маршрута без плана/активного дубля.
7. Сверить показатели аналитики с фактическими маршрутами, записями и задачами.
8. Сбросить демо и проверить восстановление исходных синтетических состояний.
